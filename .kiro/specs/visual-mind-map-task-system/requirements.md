# Документ требований: Визуальная Mind-Map система управления задачами

## Введение

Визуальная mind-map система управления задачами представляет собой интерактивное canvas-приложение с радиальной раскладкой для управления задачами, покупками и событиями. Система основана на трёх уровнях визуальных элементов (пузырей) с чёткой иерархией, поддержкой совместной работы и гибкими правами доступа.

## Глоссарий

- **System**: Визуальная mind-map система управления задачами
- **Canvas**: Интерактивная область рисования для отображения элементов системы
- **HUB**: Центральный большой пузырь, представляющий контекст (Я / Ю / Пара / Группа)
- **Cluster**: Средний пузырь, группирующий задачи одного типа
- **Task**: Малый пузырь, представляющий одну конкретную задачу
- **Bubble**: Общее название для визуальных элементов (HUB, Cluster, Task)
- **Admin**: Роль владельца кластера с полными правами
- **User**: Роль участника кластера с ограниченными правами
- **Viewer**: Роль наблюдателя с правами только на просмотр
- **Permission**: Право доступа на уровне кластера
- **Long_Press**: Долгое нажатие (1-2 секунды)
- **Drag**: Жест перетаскивания
- **Modal_Panel**: Модальная панель поверх canvas

## Требования

### Требование 1: Иерархия визуальных элементов

**User Story:** Как пользователь, я хочу видеть чёткую визуальную иерархию элементов, чтобы легко различать уровни организации задач.

#### Acceptance Criteria

1. THE System SHALL отображать три размера пузырей: малый (32px для Task), средний (96px для Cluster) и большой (128px для HUB)
2. WHEN пользователь просматривает Canvas, THE System SHALL визуально различать элементы по размеру и содержимому
3. THE Task SHALL отображать только иконку типа без текста и счётчика
4. THE Cluster SHALL отображать иконку типа, счётчик задач и метку участников
5. THE HUB SHALL отображать инициалы контекста и счётчик кластеров

### Требование 2: Создание кластера

**User Story:** Как пользователь, я хочу создавать кластеры жестом долгого нажатия и перетаскивания, чтобы быстро организовывать задачи по группам.

#### Acceptance Criteria

1. WHEN пользователь выполняет Long_Press на HUB в течение 1-2 секунд, THE System SHALL активировать режим создания кластера
2. WHEN пользователь выполняет Drag от HUB в свободную область, THE System SHALL визуально отображать создаваемый Cluster
3. WHEN пользователь отпускает палец, THE System SHALL создать новый Cluster в указанной позиции
4. WHEN Cluster создан, THE System SHALL отобразить связь от HUB к Cluster
5. WHEN Cluster создан, THE System SHALL предложить выбрать тип кластера (Task / Event / Shop / Custom)

### Требование 3: Создание задачи

**User Story:** Как пользователь, я хочу создавать задачи из кластера или из других задач, чтобы организовывать работу на детальном уровне.

#### Acceptance Criteria

1. WHEN пользователь нажимает на кнопку "+" в центре раскрытого Cluster, THE System SHALL создать новый Task в этом кластере
2. WHEN пользователь создаёт Task из другого Task, THE System SHALL создать вложенную задачу
3. WHEN Task создан, THE System SHALL увеличить счётчик Cluster на 1
4. WHEN Task создан, THE System SHALL автоматически добавить его в соответствующий Cluster
5. THE Task SHALL отображаться как малый пузырь с иконкой типа

### Требование 4: Раскрытие и сворачивание кластера

**User Story:** Как пользователь, я хочу раскрывать и сворачивать кластеры, чтобы видеть детали или получить общий обзор.

#### Acceptance Criteria

1. WHEN пользователь нажимает на Cluster, THE System SHALL раскрыть кластер в кольцо задач вокруг него
2. WHEN Cluster раскрыт, THE System SHALL скрыть счётчик и отобразить все Task как отдельные пузыри
3. WHEN пользователь повторно нажимает на раскрытый Cluster, THE System SHALL свернуть кластер обратно
4. WHEN Cluster свёрнут, THE System SHALL скрыть отдельные Task и отобразить счётчик
5. THE System SHALL анимировать переход между раскрытым и свёрнутым состояниями

### Требование 5: Счётчик задач в кластере

**User Story:** Как пользователь, я хочу видеть количество задач в кластере, чтобы быстро оценить объём работы.

#### Acceptance Criteria

1. THE Cluster SHALL отображать счётчик общего количества задач внутри
2. WHEN Task добавлен в Cluster, THE System SHALL увеличить счётчик на 1
3. WHEN Task удалён из Cluster, THE System SHALL уменьшить счётчик на 1
4. WHEN Cluster раскрыт, THE System SHALL скрыть счётчик
5. WHEN Cluster свёрнут, THE System SHALL отобразить актуальный счётчик

### Требование 6: Управление участниками кластера

**User Story:** Как администратор кластера, я хочу управлять участниками и их правами, чтобы организовать совместную работу.

#### Acceptance Criteria

1. WHEN пользователь выполняет Long_Press на метке участников "👥" кластера, THE System SHALL открыть Modal_Panel управления участниками
2. THE Modal_Panel SHALL отображать список участников с их ролями
3. THE Modal_Panel SHALL предоставлять функцию приглашения по ссылке
4. WHEN пользователь с ролью Admin изменяет права участника, THE System SHALL обновить Permission для этого участника
5. THE System SHALL отображать Modal_Panel поверх Canvas без перехода на другой экран

### Требование 7: Система ролей

**User Story:** Как владелец кластера, я хочу назначать роли участникам, чтобы контролировать уровень доступа к кластеру.

#### Acceptance Criteria

1. WHEN Cluster создан, THE System SHALL назначить создателя как Admin
2. THE System SHALL поддерживать три роли: Admin, User и Viewer
3. THE Admin SHALL иметь права на создание, удаление кластера, приглашение участников, изменение прав и просмотр всего
4. THE User SHALL иметь права на просмотр задач и выполнение разрешённых действий
5. THE Viewer SHALL иметь права только на просмотр

### Требование 8: Система прав доступа

**User Story:** Как администратор кластера, я хочу настраивать детальные права для каждого участника, чтобы гибко управлять доступом.

#### Acceptance Criteria

1. THE System SHALL хранить Permission на уровне каждого Cluster отдельно
2. THE System SHALL поддерживать права: добавление задач, выполнение задач, удаление задач, приглашение участников
3. WHEN пользователь пытается выполнить действие, THE System SHALL проверить наличие соответствующего Permission
4. WHEN у пользователя нет Permission, THE System SHALL запретить действие и отобразить уведомление
5. WHEN Admin изменяет Permission, THE System SHALL немедленно применить изменения

### Требование 9: Визуальный стиль

**User Story:** Как пользователь, я хочу видеть приятный и понятный интерфейс, чтобы комфортно работать с системой.

#### Acceptance Criteria

1. THE Canvas SHALL отображать светло-серую сетку (grid) в качестве фона
2. THE System SHALL отображать связи между HUB и Cluster как пунктирные изогнутые линии цвета #D1D5DB
3. THE System SHALL применять мягкие тени ко всем Bubble
4. THE System SHALL использовать цветовую схему: Primary #1F2937, Secondary #6B7280, Accent #3B82F6, Success #22C55E
5. THE System SHALL обеспечить визуальную согласованность всех элементов интерфейса

### Требование 10: Навигационная панель

**User Story:** Как пользователь, я хочу быстро переключаться между разными представлениями, чтобы эффективно управлять задачами.

#### Acceptance Criteria

1. THE System SHALL отображать плавающую панель навигации внизу экрана
2. THE System SHALL предоставлять четыре раздела навигации: Map, Tasks, Inbox, Calendar
3. THE System SHALL отображать панель как закруглённую с тенью, плавающую над Canvas
4. WHEN пользователь нажимает на раздел навигации, THE System SHALL переключить представление
5. THE System SHALL сохранять состояние Canvas при переключении между разделами

### Требование 11: Touch-жесты

**User Story:** Как пользователь, я хочу использовать интуитивные жесты для взаимодействия с элементами, чтобы быстро выполнять действия.

#### Acceptance Criteria

1. THE System SHALL поддерживать жест tap для выбора и активации элементов
2. THE System SHALL поддерживать жест Long_Press (1-2 секунды) для специальных действий
3. THE System SHALL поддерживать жест Drag для перемещения и создания элементов
4. WHEN пользователь выполняет жест, THE System SHALL предоставить визуальную обратную связь
5. THE System SHALL различать разные жесты и выполнять соответствующие действия

### Требование 12: Анимации

**User Story:** Как пользователь, я хочу видеть плавные анимации при взаимодействии с элементами, чтобы понимать происходящие изменения.

#### Acceptance Criteria

1. WHEN Cluster раскрывается, THE System SHALL анимировать появление Task в кольце вокруг кластера
2. WHEN Cluster сворачивается, THE System SHALL анимировать исчезновение Task и появление счётчика
3. WHEN создаётся новый элемент, THE System SHALL анимировать его появление
4. WHEN элемент перемещается, THE System SHALL плавно анимировать его движение
5. THE System SHALL обеспечить длительность анимаций не более 300ms для отзывчивости интерфейса

### Требование 13: Реал-тайм обновления

**User Story:** Как участник совместного кластера, я хочу видеть изменения других участников в реальном времени, чтобы работать синхронно.

#### Acceptance Criteria

1. WHEN другой участник изменяет Cluster, THE System SHALL обновить отображение для всех участников
2. WHEN другой участник добавляет или удаляет Task, THE System SHALL обновить счётчик Cluster для всех участников
3. WHEN другой участник изменяет права доступа, THE System SHALL немедленно применить изменения для затронутых участников
4. THE System SHALL использовать WebSocket или аналогичную технологию для реал-тайм обновлений
5. WHEN соединение потеряно, THE System SHALL уведомить пользователя и попытаться восстановить соединение

### Требование 14: Интеграция с базой данных

**User Story:** Как разработчик, я хочу использовать существующую базу данных Prisma, чтобы обеспечить согласованность данных.

#### Acceptance Criteria

1. THE System SHALL использовать Prisma для всех операций с базой данных
2. THE System SHALL хранить данные HUB, Cluster и Task в базе данных
3. THE System SHALL хранить информацию о участниках, ролях и правах в базе данных
4. WHEN пользователь выполняет действие, THE System SHALL сохранить изменения в базе данных
5. THE System SHALL обеспечить целостность данных при одновременных изменениях

### Требование 15: API для управления кластерами

**User Story:** Как разработчик, я хочу иметь API для управления кластерами, чтобы обеспечить взаимодействие клиента и сервера.

#### Acceptance Criteria

1. THE System SHALL предоставлять API endpoints для создания, чтения, обновления и удаления Cluster
2. THE System SHALL предоставлять API endpoints для управления участниками и правами
3. THE System SHALL предоставлять API endpoints для создания и управления Task
4. WHEN API запрос выполнен, THE System SHALL вернуть соответствующий HTTP статус код и данные
5. THE System SHALL валидировать все входящие данные API запросов

### Требование 16: Вложенность задач

**User Story:** Как пользователь, я хочу создавать вложенные задачи, чтобы разбивать сложные задачи на подзадачи.

#### Acceptance Criteria

1. WHEN пользователь создаёт Task из другого Task, THE System SHALL установить родительскую связь
2. THE System SHALL поддерживать неограниченную глубину вложенности Task
3. WHEN родительский Task удалён, THE System SHALL предложить удалить или переместить дочерние Task
4. THE System SHALL визуально отображать вложенность Task при раскрытии
5. THE Task SHALL учитываться в счётчике родительского Cluster независимо от уровня вложенности

### Требование 17: Типы кластеров

**User Story:** Как пользователь, я хочу выбирать тип кластера, чтобы организовывать задачи по категориям.

#### Acceptance Criteria

1. THE System SHALL поддерживать типы кластеров: Task, Event, Shop, Custom
2. WHEN Cluster создан, THE System SHALL позволить выбрать тип из списка
3. THE System SHALL отображать соответствующую иконку для каждого типа Cluster
4. WHEN тип Cluster изменён, THE System SHALL обновить иконку
5. THE System SHALL сохранять тип Cluster в базе данных

### Требование 18: Позиционирование элементов

**User Story:** Как пользователь, я хочу свободно размещать кластеры на canvas, чтобы организовать пространство по своему усмотрению.

#### Acceptance Criteria

1. THE HUB SHALL всегда находиться в центре Canvas
2. WHEN пользователь создаёт Cluster, THE System SHALL разместить его в указанной позиции
3. WHEN пользователь перемещает Cluster, THE System SHALL обновить связь с HUB
4. THE System SHALL сохранять позиции всех элементов в базе данных
5. WHEN пользователь открывает Canvas, THE System SHALL восстановить сохранённые позиции элементов

### Требование 19: Ограничения вложенности

**User Story:** Как пользователь, я хочу понимать ограничения системы, чтобы правильно организовывать задачи.

#### Acceptance Criteria

1. THE Task SHALL никогда не содержать других Bubble внутри себя
2. THE Cluster SHALL содержать только Task, но не другие Cluster
3. THE HUB SHALL содержать только Cluster, но не Task напрямую
4. WHEN пользователь пытается нарушить иерархию, THE System SHALL запретить действие
5. THE System SHALL отображать подсказку при попытке нарушения иерархии

### Требование 20: Приглашение участников

**User Story:** Как администратор кластера, я хочу приглашать участников по ссылке, чтобы легко добавлять людей в совместную работу.

#### Acceptance Criteria

1. WHEN Admin запрашивает ссылку приглашения, THE System SHALL сгенерировать уникальную ссылку для Cluster
2. THE System SHALL включить в ссылку идентификатор Cluster и токен безопасности
3. WHEN пользователь переходит по ссылке приглашения, THE System SHALL добавить его в Cluster с ролью User
4. THE System SHALL позволить Admin установить срок действия ссылки приглашения
5. WHEN ссылка приглашения истекла, THE System SHALL отклонить попытку присоединения
